Archidocs is git-native architecture as code. Each Team declares its slice of the architecture as YAML in one repo. Archidocs checks the files, combines them into one Model, and publishes a diagram viewer for people and an MCP server for agents.

The diagrams are generated from the Model at a commit, never drawn by hand, so they don't go stale. Every Element has one Owner Team, every Service has a URL per Environment, and every screen of the viewer is a link you can share. [How Archidocs works](/docs/concepts/how-archidocs-works/) shows how the parts fit together.

## Who it's for

- **People who need one answer about the architecture.** Most arrive in the viewer from a link in a pull request, a chat thread or an incident channel. The viewer needs only a browser.
- **Teams who own part of the architecture.** Each Team keeps its slice in its own folder of the repo and changes it through pull requests, as it changes code.
- **Architects** who curate Saved Views and record decisions as ADRs.
- **Coding agents,** which read and edit the same Model over MCP.

## The questions it answers

| Who | Question | In the viewer | Over MCP |
| --- | --- | --- | --- |
| Enterprise Architect | How are two Services connected? | The Connect to… Lens | [`find_paths`](/docs/reference/mcp/find_paths/) |
| Solutions Architect | Where is a Service deployed? | Where is it deployed? in the Element panel, and the Deployment Views | [`get_deployments`](/docs/reference/mcp/get_deployments/) |
| Developer | What does my Team own? | The Team Lens | [`list_owned`](/docs/reference/mcp/list_owned/) |
| Product Owner | What is upstream and downstream of an outage? | The Impact Lens | [`get_impact`](/docs/reference/mcp/get_impact/) |
| QA Tester | What is a Service's URL in a given Environment? | The Element panel | [`get_deployments`](/docs/reference/mcp/get_deployments/) |
| Technical staff | Which decisions sit behind an Element, and how has the system changed? | The ADR reader, history and Compare | [`list_adrs`](/docs/reference/mcp/list_adrs/), [`get_changes`](/docs/reference/mcp/get_changes/) |

## When it isn't the right tool

- **A one-off sketch.** Archidocs draws only what the Model holds, and you can't move a box by hand. For a whiteboard picture of an idea, a drawing tool is quicker.
- **Discovering what is running.** Archidocs shows what Teams declare. It doesn't read your clusters, cloud accounts or traces, and it doesn't detect drift from them.
- **Architecture spread over many repos.** A Workspace is one git repo. Each Team gets a folder in it, not a repo of its own.
- **A hosted service with sign-in.** The viewer is a static site you host, and the MCP server runs on your machine or in your CI. There is no shared server to sign in to.
