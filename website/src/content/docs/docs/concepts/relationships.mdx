A [Relationship](/docs/reference/glossary/#term-relationship) is a directed edge from a consumer Element to the provider it depends on. It is declared once, under the consumer, with `to` naming the provider.

```yaml file="examples/big-bank/archidocs/payments/model.yaml" region="payments-service"
```

The `description` reads as a sentence from consumer to provider: "Payments Service posts payments to the ledger in Mainframe". The `technology` says how: a protocol, a driver or a format. The [Elements and Relationships reference](/docs/reference/model/model-yaml/) lists every field.

## One direction

A Relationship always points from what depends to what is depended on. Everything [upstream](/docs/reference/glossary/#term-upstream-downstream) of an Element depends on it, directly or through others. Everything downstream is what it depends on.

A Person is only ever a consumer: it uses Systems, and nothing depends on it. `archidocs check` reports a Relationship to a Person as [`person-as-provider`](/docs/reference/rules/person-as-provider/). An Element also can't depend on itself, its parent or its child.

## Declared once, derived above

Declare a Relationship at the most detailed level you know. If you know which Component calls which, declare it between those Components. If not, declare it between the Services.

Edges between higher-level Elements are derived from these, never declared. Because the Payments Service calls `core:mainframe`, the C2 landscape draws an edge from Payments Service to Mainframe. The C1 landscape draws one from the Payments System to the Mainframe Banking System. In the viewer, select an edge to see every Relationship it carries.

## Between Projects

Each Project declares only its own outbound Relationships. To name a provider in another Project, write its [Qualified id](/docs/reference/glossary/#term-qualified-id), the id with its Project in front, as `core:mainframe` above.

## Events and brokers

A Relationship is a call by default: `interaction: sync`, which waits for an answer. An event that goes through a message broker is `async`. The [Subscriber](/docs/reference/glossary/#term-subscriber), the Element that receives the events, declares it. It points `to` the [Publisher](/docs/reference/glossary/#term-publisher) that sends them, with `via` naming the broker Service and `channel` the topic or queue.

Impact and path questions count the broker as a hop, and as something both sides depend on. An async Relationship with no broker, such as a webhook, leaves out `via`.

## Several Relationships on one pair

A consumer can depend on the same provider in two ways, such as reading over HTTPS and subscribing to events. Give each Relationship an `id` then, so Dynamic View Steps and agents can tell them apart.

## Why it works this way

- **Consumer to provider, so impact questions have an answer.** Every edge points the same way, so "what breaks if the mainframe is down?" is everything upstream of it. A model that mixed directions couldn't say.
- **The consumer declares it, because the consumer knows.** A Team knows what its Service calls, but rarely everything that calls it. Declaring under the consumer means each Team writes down what it depends on, in its own Project. Nobody edits another Team's files to add a Relationship that points at them, and a Relationship belongs to its consumer's Owner.
- **The Subscriber declares an event for the same reason.** The Subscriber depends on the events, so the edge points from it to the Publisher, like any other Relationship. A Publisher doesn't need to know who listens.
- **Higher-level edges are derived, so they can't drift.** Each derived edge carries every Relationship beneath it. If the C2 edge were declared separately, it could say something the Components don't, and nothing would catch it.
