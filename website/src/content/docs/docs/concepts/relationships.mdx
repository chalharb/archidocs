A [Relationship](/docs/reference/glossary/#term-relationship) is a directed edge from a **consumer** to the **provider** it depends on. It is declared under the consumer, with `to` naming the provider:

```yaml file="examples/big-bank/archidocs/payments/model.yaml" region="payments-service"
```

The `description` reads as a sentence from consumer to provider: "Payments Service posts payments to the ledger in Mainframe". `technology` says how: a protocol, a driver, a format.

## One direction

A Relationship always points from what depends to what is depended on. That is what makes impact questions answerable: everything [upstream](/docs/reference/glossary/#term-upstream-downstream) of the mainframe depends on it, and an outage there reaches all of it.

A Person is only ever a consumer: it uses Systems, and nothing depends on it. Pointing a Relationship at a Person is an error:

```yaml file="website/samples/person-provider/archidocs/shop/model.yaml" fails="person-as-provider"
```

`archidocs check` reports [`person-as-provider`](/docs/reference/rules/person-as-provider/). Declare it the other way round, under the Person. An Element also can't depend on itself, its parent or its child ([`ancestor-descendant-relationship`](/docs/reference/rules/ancestor-descendant-relationship/)).

## Declared once, derived above

Declare a Relationship at the most detailed level you know. If the code shows which Component calls which, declare it between those Components; if not, between the Services. Big Bank's API Application declares its dependencies on its Components:

```yaml file="examples/big-bank/archidocs/digital/model.yaml" region="api"
```

Edges between higher-level Elements are derived from these and never declared: because the Mainframe Banking System Facade calls `core:mainframe`, the C2 Landscape draws an edge from API Application to Mainframe, and the C1 Landscape one from Internet Banking System to Mainframe Banking System. Declaring the same edge again at a higher level would only let the two drift apart.

## Between Projects

Each Project declares only its own outbound Relationships, so each Team writes down what it depends on and nobody edits another Team's files to add an inbound one. Name a provider in another Project by its Qualified id, as `core:mainframe` above.

## Async Relationships and brokers

A Relationship is `interaction: sync` by default: a call that waits for an answer. An event that goes through a message broker is `async`, and is declared by the [Subscriber](/docs/reference/glossary/#term-subscriber), pointing `to` the [Publisher](/docs/reference/glossary/#term-publisher) whose events it depends on, with `via` naming the broker Service and `channel` the topic or queue:

```yaml file="examples/big-bank/archidocs/payments/model.yaml" region="fraud-detection"
```

Fraud Detection depends on Payments Service's `payments.initiated` events, carried by the Platform Team's Kafka. Impact and path questions count the broker as a hop, and as a dependency of both sides. An async Relationship with no broker, such as a webhook, leaves out `via`.

## Several Relationships on one pair

When a consumer depends on the same provider in two ways, such as reading over HTTPS and subscribing to events, give each Relationship an `id`, unique in the Project ([`duplicate-relationship-id`](/docs/reference/rules/duplicate-relationship-id/)), so Dynamic View Steps and agents can tell them apart.
