A [View](/docs/reference/glossary/#term-view) is a diagram defined by a query over the Model. It is never a source of truth: it picks Elements and draws them, and the Model decides what they are and how they connect.

## Generated Views

A [Generated View](/docs/reference/glossary/#term-generated-view) exists for every scope without anyone writing it:

| View id | Shows |
| --- | --- |
| `c1` | The System landscape: every Person and System. |
| `c2` | The Service landscape: every Service, grouped in its System. |
| `c2/<system>` | One System's Services, with what they connect to. |
| `c3/<service>` | One Service's Components, with what they connect to. |
| `deployment/<environment>` | Every Deployment in one Environment, on its Targets. |

They cover most questions. The viewer opens on `c2`.

## Saved Views

A [Saved View](/docs/reference/glossary/#term-saved-view) is a View written into a Project's files, for a question the Generated Views don't answer at a glance. It has a Qualified id, such as `digital:mainframe-outage`.

A Saved View says which Elements to include, and the level to draw them at. It can pick Elements by id, by what is upstream or downstream of one, by Team, by tag, or by the paths between two. The [Saved Views reference](/docs/reference/model/views-yaml/) lists every selector.

The selectors keep working as the Model changes. A new Service that depends on the mainframe joins the View above without anyone editing it.

## Lenses

A [Lens](/docs/reference/glossary/#term-lens) highlights part of a View without changing which nodes it shows:

- **Impact**: what is upstream, downstream, or both, of one Element, each node marked with how many hops away it is.
- **Team**: what one Team owns.
- **Path**: the paths between two Elements.

The viewer turns Lenses on and off. A Saved View can open with one, as `mainframe-outage` opens with Impact.

## Deployment Views

A [Deployment View](/docs/reference/glossary/#term-deployment-view) places Deployments on their Deployment Targets in one Environment. Each Environment has a Generated one, and a Saved View can narrow it to some Services or Targets. See [Deployments](/docs/concepts/deployments/#deployment-views).

## Dynamic Views

A [Dynamic View](/docs/reference/glossary/#term-dynamic-view) shows one scenario, drawn as a sequence chart. It is an ordered list of [Steps](/docs/reference/glossary/#term-step), each one interaction:

<Diagram view="big-bank/payments:make-a-payment" alt="A Big Bank customer makes a payment: numbered Steps from the customer through the app and the Payments Service to the mainframe, with the payment events and the reply." />

Each Step must follow a Relationship that exists in the Model. See [Dynamic Views](/docs/guides/model/dynamic-views/).

## Layout

The [Layout](/docs/reference/glossary/#term-layout), where each node sits on the diagram, is computed every time a View is drawn. It is never stored. A View says only which way it runs: top to bottom, left to right, or the reverse of either.

## Why it works this way

- **A View is a query, so it can't go stale.** It never stores the Elements it shows. When the Model changes, every View that the change touches redraws, and a new Service joins every View whose selectors pick it.
- **Layout is never stored, so it can't carry meaning.** If positions were saved, a box's place could start to mean something the Model doesn't say, and every Model change would leave old positions to fix. Computing the Layout keeps the Model the only truth. It also keeps View files free of coordinates, so they diff cleanly in a pull request.
- **Generated Views for every scope.** Nobody has to write and maintain a diagram for each System and Service. A Saved View is only for a question worth naming.
- **Steps follow Relationships.** A scenario can't show a call the architecture doesn't have. If a Relationship is removed, `archidocs check` reports every Step that used it.
