A [Workspace](/docs/reference/glossary/#term-workspace) is the whole architecture landscape, kept in one git repository. Archidocs reads it from a folder in that repo, `archidocs/` by default, which holds one `workspace.yaml` and a folder per Project.

```text
archidocs/
├── workspace.yaml        # Teams and Environments, for every Project
├── payments/
│   ├── project.yaml      # id, name and owner Team
│   ├── model.yaml        # Elements and Relationships
│   ├── deployments.yaml  # Deployment Targets and Deployments
│   ├── views.yaml        # Saved Views
│   └── adr/              # architecture decision records
└── core/
    └── ...
```

## The Workspace file

`workspace.yaml` defines what every Project shares: the [Teams](/docs/concepts/teams-and-ownership/) that own things and the [Environments](/docs/concepts/deployments/) that Services run in. Each is defined once, so `prod` means the same thing in every Project. This is Big Bank's:

```yaml file="examples/big-bank/archidocs/workspace.yaml"
```

Nothing else goes in it: Elements, Deployments and Views always belong to a Project. Every field is in the [`workspace.yaml` reference](/docs/reference/model/workspace-yaml/).

## Projects

A [Project](/docs/reference/glossary/#term-project) is one Team's slice of the Workspace, kept in a folder of its own. A `project.yaml` marks the folder, gives the Project its id, and names the Team that owns what is declared in it:

```yaml file="examples/big-bank/archidocs/payments/project.yaml"
```

Every other `.yaml` file in the folder is part of the Project's Model, whatever its name. `model.yaml`, `deployments.yaml` and `views.yaml` are a convention: Big Bank's Platform Project keeps its Services in `services.yaml` and its Deployment Targets in `targets.yaml`. Projects don't nest, and a `.yaml` file outside any Project is an error ([`file-outside-project`](/docs/reference/rules/file-outside-project/)).

Because each Team edits only its own folder, a `CODEOWNERS` file can route every change to the Team that owns it.

## Ids

Everything in a Project has an id: a lowercase slug such as `payments-service`, unique across the Project's Elements and Deployment Targets. Inside its own Project an id is written bare. To name something in another Project, write its [Qualified id](/docs/reference/glossary/#term-qualified-id), `project:id`. Here the Payments Service depends on the mainframe that the Core Banking Team declares in its `core` Project:

```yaml file="examples/big-bank/archidocs/payments/model.yaml" region="payments-service"
```

`payments-db` and `card-gateway` are in the same Project, so they are bare. Writing a Project's own prefix is an error, so that every id has one spelling:

```yaml file="website/samples/own-prefix/archidocs/shop/model.yaml" fails="own-project-prefix"
```

`archidocs check` reports it as [`own-project-prefix`](/docs/reference/rules/own-project-prefix/): write `to: api` instead. Teams and Environments belong to the Workspace, so their ids are always bare.

## One Model

`archidocs check` and every other command read all the Projects together as one [Model](/docs/reference/glossary/#term-model), checking every reference across them. The viewer and the MCP server never see Projects as separate diagrams: they show and answer questions about the whole Workspace, with each Element marked with the Team that owns it.
