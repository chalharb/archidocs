A [Workspace](/docs/reference/glossary/#term-workspace) is the whole architecture, kept in one git repo. Each Team edits its own [Project](/docs/reference/glossary/#term-project), a folder in the Workspace that holds the Team's slice of the Model.

<FileTree>
- archidocs/
  - workspace.yaml Teams and Environments, for every Project
  - payments/
    - project.yaml the Project's id, name and owner Team
    - model.yaml Elements and Relationships
    - deployments.yaml Deployment Targets and Deployments
    - views.yaml Saved Views
    - adr/ architecture decision records
  - core/
    - …
</FileTree>

## The Workspace file

`workspace.yaml` marks the Workspace's folder, `archidocs/` by default. It defines what every Project shares: the [Teams](/docs/concepts/teams-and-ownership/) that own things and the [Environments](/docs/concepts/deployments/) that Services run in. Each is defined once, so `prod` means the same thing in every Project.

Nothing else goes in it. Elements, Deployments and Views always belong to a Project. The [`workspace.yaml` reference](/docs/reference/model/workspace-yaml/) lists its fields.

## Projects

A `project.yaml` marks a Project's folder. It gives the Project its id and names the Team that owns what is declared in it. The [`project.yaml` reference](/docs/reference/model/project-yaml/) lists its fields.

Every other `.yaml` file in the folder is part of the Project's Model, whatever its name. `model.yaml`, `deployments.yaml` and `views.yaml` are only a convention: Big Bank's Platform Project keeps its Services in `services.yaml`.

Projects don't nest. A `.yaml` file outside every Project is an error, which `archidocs check` reports as [`file-outside-project`](/docs/reference/rules/file-outside-project/).

## Ids

Everything in a Project has an id: a lowercase slug such as `payments-service`, unique in the Project. Inside its own Project an id is written bare.

To name something in another Project, write its [Qualified id](/docs/reference/glossary/#term-qualified-id), the id with its Project in front: `core:mainframe`. Here the Payments Service depends on the mainframe that the Core Banking Team declares in its `core` Project:

```yaml file="examples/big-bank/archidocs/payments/model.yaml" region="payments-service"
```

`payments-db` and `card-gateway` are in the same Project, so they are bare. Writing a Project's own prefix is an error, [`own-project-prefix`](/docs/reference/rules/own-project-prefix/). Teams and Environments belong to the Workspace, so their ids are always bare.

## One Model

`archidocs check` and every other command read all the Projects together as one [Model](/docs/reference/glossary/#term-model), every Element and Relationship in the Workspace. They check every reference across Projects.

The viewer and the MCP server never show Projects as separate diagrams. They show the whole Workspace, with each Element marked with the Team that owns it.

## Why it works this way

- **One repo, one commit.** Every Project is read at the same commit, so there are no versions to pin between them. A Workspace Bundle, the combined Model, records the one commit it was built from.
- **A folder per Team.** Each Team edits only its own folder, so a `CODEOWNERS` file can route every change to the Team that owns it.
- **No list of Projects.** A folder with a `project.yaml` is a Project. Adding a Team's Project never means editing a shared file.
- **Qualified ids, even in one repo.** With dozens of Teams, ids such as `api` or `db` would clash. A Project prefix keeps every id unique, and would let Projects move to repos of their own later without renaming anything.
- **One spelling per id.** A Project can't prefix its own ids, so inside a Project each thing is written one way, and a prefix always means another Project.
