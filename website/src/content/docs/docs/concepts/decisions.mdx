An [ADR](/docs/reference/glossary/#term-adr), an architecture decision record, records one decision: the problem, the options considered, what was chosen and what follows from it. Archidocs keeps each ADR as a Markdown file in the Project that owns the decision, linked to the Elements and Saved Views it affects.

```markdown file="examples/big-bank/archidocs/payments/adr/0002-hold-payments-on-a-high-fraud-score.md"
```

## An ADR file

Each ADR is a file in its Project's `adr/` folder, named with a four-digit number and a slug of its title, such as `0002-hold-payments-on-a-high-fraud-score.md`. The number is unique in the Project. The body is ordinary Markdown under one `#` title.

The frontmatter carries the decision's status and date, the people who took part, and its links. The [ADR frontmatter reference](/docs/reference/model/adr-frontmatter/) lists every field and status.

## Linked to the Model

An ADR's links name Elements, Deployment Targets and Saved Views. They are checked like any other reference in the Model, so a link to an id that doesn't exist fails `archidocs check`. Links to another Project use Qualified ids.

Links are optional. A decision for the whole Workspace, such as "every Service emits OpenTelemetry", can link nothing.

## Proposed, then accepted

A decision starts as `proposed`, in a pull request. Reviewing the pull request is reviewing the decision, next to the Model changes it brings. Accepting it means setting `status: accepted` and the date before the merge.

A Proposed ADR is still shown, marked as proposed, so nobody mistakes it for the architecture as it is.

## Superseded

When a later decision replaces an earlier one, the new ADR lists the old one in `supersedes`. Once the new ADR is accepted, Archidocs derives that the old one is superseded, and shows it so.

The old file isn't edited and keeps the status it had. Writing `superseded` by hand is an error, [`hand-written-superseded`](/docs/reference/rules/hand-written-superseded/).

## Decisions in the viewer and MCP

The Element panel lists the ADRs linked to an Element, and the ADR reader opens one beside the diagram. Over MCP, [`list_adrs`](/docs/reference/mcp/list_adrs/) and [`get_adr`](/docs/reference/mcp/get_adr/) read them. [`propose_adr`](/docs/reference/mcp/propose_adr/) writes a new one, with the next free number and today's date.

## Why it works this way

- **ADRs live beside the Model.** A decision and the Model change it brings arrive in the same pull request, are reviewed together, and share one history.
- **In the Project that owns the decision.** Each Team keeps its own decisions, numbered in its own Project. A decision that spans Projects lives in the Project that made it, and links the others by Qualified id.
- **Accepting is a review, so it happens in the pull request.** The status change is the act of approval. No tool accepts an ADR on its own: a person or an agent edits the status, and the pull request is reviewed like any other.
- **`superseded` is derived, never written.** "B replaces A" is declared once, on B. If A also had to say "superseded by B", the two files could disagree, and editing an accepted decision's file would blur what was decided. The trade-off: reading A's file raw in git still shows its old status, while the viewer and MCP show it as superseded.
