An [ADR](/docs/reference/glossary/#term-adr), an architecture decision record, records one decision: the problem, the options considered, what was chosen and what follows from it. Archidocs keeps ADRs in the Project that owns the decision, as Markdown files in its `adr/` folder, and links each one to the Elements, Deployment Targets and Saved Views it affects.

## An ADR file

Each ADR is `<project>/adr/NNNN-slug.md`: a four-digit number, unique in the Project, and a slug of its title. Its frontmatter carries the status and the links; its body is ordinary Markdown under one `#` title:

```markdown file="examples/big-bank/archidocs/payments/adr/0002-hold-payments-on-a-high-fraud-score.md"
```

- `status` is `proposed`, `accepted`, `rejected`, `deprecated` or `superseded`, and `date` is when it last changed.
- `elements` and `views` link the decision to the Model. They are checked like any other reference ([`unknown-adr-link`](/docs/reference/rules/unknown-adr-link/)), and use Qualified ids for other Projects.
- `decision-makers`, `consulted` and `informed` say who took part. They aren't checked.

Every field is in the [ADR frontmatter reference](/docs/reference/model/adr-frontmatter/).

## Proposed, then accepted

A decision starts as `proposed`, in a pull request. Reviewing the pull request is reviewing the decision, next to the Model changes it brings; accepting it is setting `status: accepted` and the date before the merge. A Proposed ADR is still shown, marked as proposed, so nobody mistakes it for the architecture as it is.

## Superseded

When a later decision replaces an earlier one, the new ADR lists it in `supersedes`, and Archidocs derives that the old one is superseded. The old ADR keeps the status it had: writing `superseded` by hand is an error ([`hand-written-superseded`](/docs/reference/rules/hand-written-superseded/)), so the record of what replaced what lives in one place. Big Bank's Digital Banking Team superseded its first sign-in decision when it moved sign-in to the Identity Platform.

## Decisions in the viewer and MCP

The Element panel lists the ADRs linked to an Element, and the ADR reader opens one beside the diagram, so the decisions behind an Element are one click away from it. Over MCP, [`list_adrs`](/docs/reference/mcp/read-tools/#list_adrs) and [`get_adr`](/docs/reference/mcp/read-tools/#get_adr) read them, and [`propose_adr`](/docs/reference/mcp/write-tools/#propose_adr) writes a new one with the next free number and today's date.
