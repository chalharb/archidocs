Every pull request runs `archidocs check`, without building or publishing, so a change that breaks the Model fails before it merges.

## Before you start

- The [Workspace](/docs/reference/glossary/#term-workspace), the whole architecture kept in one repo, is in a GitHub or GitLab repo, and `archidocs check` passes on the default branch. See the [Quick start](/docs/start/quick-start/).
- The repo doesn't build [pull request previews](/docs/guides/publish/pr-previews/) yet. A preview job already checks every pull request.

## 1. Add the job

<Tabs syncKey="ci">
<TabItem label="GitHub">

Add this workflow to the repo:

```yaml file="examples/ci/.github/workflows/check.yml" title=".github/workflows/check.yml"
```

`--format github` prints each issue as a GitHub Actions annotation. The pull request then shows the issue on the line it is about.

</TabItem>
<TabItem label="GitLab">

Add this job to the repo's `.gitlab-ci.yml`:

```yaml file="examples/ci/.gitlab-ci.yml" title=".gitlab-ci.yml"
```

GitLab has no annotations for this. The job's log lists each issue with its file, line and rule.

</TabItem>
</Tabs>

`--strict` fails the job on warnings as well as errors, so warnings don't pile up. Drop it to fail on errors only.

## 2. Pin the CLI version

The job installs `archidocs@1`, the latest 1.x release. To upgrade only when you choose, write the exact version you run locally:

```bash
archidocs version
```

```text
archidocs 1.2.0 (Bundle schemaVersion 1)
```

Then replace `archidocs@1` in the job with that version, such as `archidocs@1.2.0`.

## 3. Require the check

So that a failing check blocks the merge:

- **GitHub:** add a branch ruleset for the default branch that requires the `check` status check.
- **GitLab:** turn on **Settings › Merge requests › Pipelines must succeed**.

## Check it worked

Open a pull request that adds a field that doesn't exist, such as `colour: red` under a [System](/docs/reference/glossary/#term-system). The job fails. On GitHub, its log shows the annotation it printed:

```text
::error file=archidocs/digital/model.yaml,line=15,col=5,title=unknown-field::Unknown field "colour" See https://archidocs.dev/docs/reference/rules/unknown-field/
```

The pull request's **Files changed** tab shows the message on line 15. Remove the field and push: the job passes.

## If it didn't

If the job fails with `No workspace.yaml found`, the Workspace is in another folder of the repo. On GitHub, set `working-directory` to its folder on the `check` step. On GitLab, add `cd <folder>` before `archidocs check`.

If the job fails on an issue, the message links the rule's page, such as [`unknown-field`](/docs/reference/rules/unknown-field/). The page says how to fix it.

If a new release fails the job on a warning that you can't fix yet, pin the version you ran before, as in step 2.

## With an agent

The [`check`](/docs/reference/mcp/write-tools/#check) tool runs the same check over MCP. An agent that edits the Model can run it before it opens the pull request, so CI finds nothing new.
